# v0.5 plan: the chat in the agent panel

Goal: the agent panel can show a conversation drawn by the app instead of
agy's terminal interface: messages, collapsible command blocks, and Run /
Don't Run buttons for the agent's commands.

## How it works

```
┌──────────────────────────── Aiterm window ─────────────────────────────┐
│ [The agent wants to run: apt install htop]  [Don't Run] [Run]          │
│  your shell                            │  chat: messages, ▸ $ commands │
└────────────▲───────────────────────────┴──────────▲───────────┬────────┘
             │ D-Bus (RunCommand waits for Run)     │ NDJSON    │ NDJSON
             │                                      │ events    │ messages
             │          ┌────────────┐ MCP  ┌───────┴───────────▼────────┐
             └──────────│ aiterm-mcp │◄─────│ agy --input-format         │
                        └────────────┘      │     stream-json            │
                                            │     --output-format        │
                                            │     stream-json --print    │
                                            └────────────────────────────┘
```

- **agy as a backend.** `agy --print --input-format stream-json
  --output-format stream-json` keeps one conversation open: each line written
  to its stdin (`{"event": "user", "message": {"content": "…"}}`) runs a
  turn, and stdout streams typed events: `init`, `step_update` (the user's
  message, the agent's text in deltas, each tool call with its parameters
  and output, token usage) and one `result` per turn. The chat reads these
  and draws them. Stop kills the process; the next message resumes the
  same conversation with `--conversation <id>`.
- **Approval lives in the app.** Print mode cannot ask the user anything:
  a tool that needs permission is refused. So agy is allowed to call the
  aiterm tools, and the app asks instead: `RunCommand` shows the command in
  a bar above the user's terminal and types it only after Run. This works
  the same with agy's own interface in the panel, and nothing the agent is
  told or configured can skip it. A preference turns it off for hands-free
  use; `sudo` still needs the user's password every time.
- **Two views.** Preferences → Agent → View: *Terminal* (agy's own
  interface, as in v0.3, with its slash commands and settings) or *Chat*.
  Terminal stays the default, so nothing changes for a current user until
  they switch.

## Chat view

- Messages: the user's on the right, the agent's as text with simple
  Markdown (code, bold, code blocks) drawn with Pango markup.
- Tool calls: `run_command` is a collapsible block, `$ command` with its
  output and exit code (red when it failed); other tools are one quiet line
  (`Read file …`). While a tool runs, its line shows a spinner.
- The input at the bottom: Enter sends, Shift+Enter is a new line, Stop
  while a turn runs.
- The turn's token usage goes in a quiet line under the answer: it is the
  number v0.6's evals measure, so it is good to see it in daily use.

## Steps

1. [x] **Approval in the app**: the approval bar, the preference, `denied`
   in the D-Bus API, the MCP server and `aiterm-run`; the installer allows
   all four tools in agy. (Also: an ended command now waits for its prompt
   before it is logged, so a `run_command` right after `wait_for_command`
   is not mistaken for typed text.)
2. [x] **Chat view**: `chat.py` (the agy process and the event stream),
   `chat_view.py` (the widgets), the View preference. Tested with a fake agy
   that speaks the same NDJSON and calls the real tools.
3. [x] **Docs**: README, roadmap.

## Out of scope for v0.5

- Slash commands, model switching and agy's settings in the chat (switch to
  the Terminal view for those)
- Showing the agent's file edits as diffs
