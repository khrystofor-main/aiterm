# v0.6 plan: evals

Goal: measure whether the agent fixes a broken setup through aiterm's tools,
automatically and in isolation, and publish the numbers in the README.

## How a run works

```
evals/run.py
  │ 1. setup.sh in the sandbox         ┌──── Aiterm window (real app) ─────┐
  │ 2. opens a window whose shell ────►│ bwrap: bash + shell integration   │
  │    is sandboxed, types history     │ no network, no sudo, private home │
  │ 3. agy -p "<prompt>" ──MCP──► aiterm-mcp ──D-Bus──► RunCommand …      │
  │    --output-format stream-json     └───────────────────────────────────┘
  │ 4. check.sh in the same sandbox → solved?
  └ 5. metrics → evals/results/latest.json, README table
```

- **The real app, not a mock.** The runner drives the same GTK window,
  command log, D-Bus API and MCP server a user has. Only the shell is
  wrapped: `Window(argv=...)` starts `bwrap … bash --rcfile integration.bash`.
- **Isolation with bubblewrap** (no root, already on Ubuntu): the system is
  bound read-only; `/home`, `/tmp`, `/run`, `/media`, `/mnt` are empty
  except the run's own home, bound at the same path as on the host so the
  agent's file tools and the terminal agree on paths; no network (so no
  downloads and no session bus), no `sudo` (no new privileges). A scenario
  that needs a package can only be solved by telling the user.
- **agy as in the panel, but clean.** One `agy -p` per run, in the project
  folder, with `AITERM_WINDOW` pointing at the eval window. Its `HOME` is a
  temp folder with only the user's login files linked, the aiterm plugin,
  and permission for the aiterm tools only. So the user's `GEMINI.md` and
  settings don't leak into the measurement, and agy's own hidden shell is
  refused, which is counted as a metric (it should be 0).
- **Checks are tested too.** Each scenario has `solution.sh` (and
  `answer.txt` when the answer matters); `tests/eval_scenarios.py` checks
  that every `check.sh` fails on the broken setup and passes after the
  solution, without the agent, as part of `tests/run.sh`.

## Metrics

| Metric | From |
|---|---|
| Solved | `check.sh` exit code, and agy's result status |
| Steps | tool calls in agy's `step_update` events |
| Commands (failed) | the command log of the eval terminal |
| Hidden shell | agy's own `run_command` tool calls (refused) |
| Tokens, time | the `result` event's `usage` and `duration_seconds` |

## Found on the way

A shell started under a wrapper (`bwrap`, also `toolbox`) is not the
spawned process, so the terminal took the idle shell for a running program
and `run_command` refused everything. The terminal now remembers the
shell's process group at its first prompt.

## Out of scope for v0.6

- Running the evals in CI: they need a signed-in agy and a desktop session
  (the tests that don't, including the scenario checks, run in CI in v1.0)
- Comparing many models: `--model` exists, the README shows one
